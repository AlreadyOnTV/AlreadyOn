01 / HOW THE PIECES FIT

How the pieces fit

One server reads your media, stores library/settings/schedules in SQLite, and serves the WebUI, API and streams over HTTPS. Browsers and native apps connect to that server; GitHub Pages hosts only this informational website. Media is not uploaded to the website.

The published image targets Linux amd64. Begin with an x86-64 Linux Docker host or a NAS with compatible Compose support, a persistent configuration volume, readable media and a client on a trusted LAN. CPU/RAM/network needs depend on codecs, resolution, tone mapping and concurrent viewers. GPU availability alone does not establish HDR or client compatibility.

Delivery chooses direct play when supported, remuxing when the container needs changing, or transcoding when media must be converted. Direct-play files do not benefit from a faster video encoder. Test a small representative library before planning capacity.

02 / INSTALL WITH DOCKER COMPOSE

Install with Docker Compose

  1. Install Docker Engine and its Compose plugin. Create a dedicated application directory.
  2. Save the example as compose.yaml. Replace the media path, timezone and user/group IDs with your host’s values. Use id -u and id -g to inspect IDs; the config directory needs write access and media needs read access.
  3. Run docker compose config --quiet, then docker compose up -d.
  4. Open https://YOUR-SERVER-IP:19900, verify the instance/address before trusting its initial certificate, and create the server name and owner account.
  5. Add container-side media paths and test playback using the usage guide.
compose.yaml · LAN, CPU-only
services:
  alreadyon:
    image: ghcr.io/alreadyontv/alreadyon:stable
    restart: unless-stopped
    ports:
      - "19900:19900"
    environment:
      PUID: "1000"
      PGID: "1000"
      TZ: America/New_York
    volumes:
      - ./config:/config
      - /YOUR/MEDIA/FOLDER:/data/media:ro

:ro protects media from container writes. Do not mount a live library as disposable test data. Persist and back up /config; replacing the container is different from deleting its database. stable is the approved main channel, latest is test, and nightly is development. Use a known image digest for an exactly reproducible deployment.

The repository Compose example also covers GPU devices and optional transcode scratch storage. Size a RAM-backed scratch directory for your workload; it consumes host memory.

03 / WHY HTTPS IS REQUIRED

Why HTTPS is required

UI, API and media share the encrypted application listener on TCP 19900 by default. Login sessions, profile actions and playback credentials need protection on every connection. Plain HTTP upstream termination is unsupported for browser sessions; a reverse proxy must use verified HTTPS upstream or pass TLS through.

A fresh installation creates its own instance CA. For browser access, import that CA only on devices you control and use a hostname covered by the certificate. Check the selected instance before trusting it. A browser warning does not justify turning off validation globally.

Native Android/TV onboarding saves trust inside the app for the selected server; it does not install a device-wide CA. Saved trust failures block connections and require an explicit CA replacement decision. Initial trust on an untrusted network cannot detect an impersonated server, so perform first connection on your trusted LAN.

Uploaded certificates apply to new connections immediately and persist across restarts. Make sure the hostname you will use works before switching; an uncovered localhost/IP URL may stop validating. A certificate downloaded from a proxy is not a substitute for its private key and issuing chain.

AlreadyOn’s current WebUI ACME flow uses HTTP-01. If you obtain a DNS-01 certificate with an external client, use the uploaded-certificate flow and manage renewal yourself. Let’s Encrypt documents the challenge differences.

04 / HARDWARE TRANSCODING

Hardware transcoding

Start with Software Only and a working playback baseline. Under Server → Server, Hardware Encoding offers Intel, AMD and NVIDIA; Hardware Decoding is separate and requires a hardware encoder. The Test actions report the chosen path. Save the setting, then test real representative files and clients.

Intel and AMD

Install the host’s appropriate GPU driver and expose the render device to the container. Add this inside the AlreadyOn service:

devices:
  - /dev/dri:/dev/dri

Check host device permissions with stat -c '%g %n' /dev/dri/*. An explicit non-root container user may require matching supplemental groups; use the actual host GIDs, not copied examples. Intel can use QSV where the tested hardware supports it, with VA-API fallback; AMD uses VA-API. Confirm the Test result rather than inferring capability from the vendor name.

NVIDIA

Install a compatible host driver and NVIDIA Container Toolkit, then reserve a video-capable GPU. This service fragment follows the app’s GPU setup:

deploy:
  resources:
    reservations:
      devices:
        - driver: nvidia
          count: 1
          capabilities: [gpu, video]

See Docker’s GPU reservation reference for host/Compose requirements.

Encoding is not the whole pipeline

Encoding alone leaves decoding, scaling and HDR-to-SDR tone mapping on the CPU. Hardware Decoding attempts to move those stages to the GPU too, with per-file fallback. Unsupported codecs, drivers and HDR conversions can still consume CPU. Monitor Dashboard and test direct play, conversion, channel changes and multiple viewers separately. A passing synthetic encoder test is not complete hardware certification.

05 / PORTS, FIREWALLS AND REMOTE ACCESS

Ports, firewalls and remote access

First make LAN playback work. Give the server a stable LAN address. If you choose public access, point your domain at the public IP, create only the needed firewall/NAT rules and test from a separate external network. DDNS updates DNS; it does not make a blocked port reachable.

UsePublic / host sideContainer destination
LAN apps and discoveryHost TCP 19900HTTPS TCP 19900
Direct public viewingWAN TCP 443 → host TCP 443HTTPS TCP 19900, using mapping 443:19900
Built-in HTTP-01 validationWAN TCP 80 → host TCP 80Challenge TCP 19902, using mapping 80:19902

For direct public hosting, add 443:19900 and, if using the app’s HTTP-01 certificate flow, 80:19902 to Compose ports. Keep 19900:19900 for native LAN discovery/sign-in. The challenge listener serves ACME validation only; it is not a normal HTTP site or redirect. HTTP-01 requires public port 80, even though its container-side port is different.

Keep the validation route for renewal. Check both A and AAAA records; a stale IPv6 record can send clients/validation to another host. Carrier-grade NAT, ISP filtering or double NAT can prevent inbound access even when Compose is correct. Fix that network boundary before retrying certificate issuance.

If a proxy already owns host ports 80/443, do not bind a second service to them. Choose which service owns public TLS and ACME, then route validation and traffic consistently. Native account-PIN sign-in still requires a direct LAN peer; publishing the WebUI does not turn it into an internet pairing endpoint.

06 / DYNAMIC DNS

Dynamic DNS

In Server → Server → Dynamic DNS, choose None, Cloudflare or No-IP. None disables the app’s updater; a router or other external DDNS service can still manage your hostname.

  1. Create the hostname/provider account and make sure the domain or DNS zone is active.
  2. For Cloudflare, use a zone-scoped token with DNS Edit and Zone Read. AlreadyOn discovers the zone and creates/updates the IPv4 A record in DNS-only mode; it disables proxying on that record.
  3. For No-IP, enter the actual full hostname and update credentials/DDNS Key. A provider group alias is not the hostname.
  4. Save Changes to store the configuration and trigger an initial sync. Review last attempt, success/failure and next retry in the status.

Checks run about every five minutes and failures back off. The updater manages IPv4 A records; inspect existing AAAA records separately. Provider account obligations, such as No-IP hostname confirmation, remain yours. Stored credentials are not returned to the form; reveal controls expose only a replacement draft.

DNS and certificate names should agree with the URL viewers use. DDNS neither opens firewall ports nor installs a publicly trusted certificate.

07 / NGINX PROXY MANAGER AND TRAEFIK

Nginx Proxy Manager and Traefik

A proxy is optional; direct HTTPS works without one. Two architectures preserve the application’s encrypted upstream:

  1. TLS passthrough: route the TCP connection unchanged to AlreadyOn:19900. AlreadyOn presents the certificate; the proxy does not decrypt the stream.
  2. TLS termination plus HTTPS upstream: the proxy presents its public certificate and creates a second, verified HTTPS connection to AlreadyOn:19900. Mount the instance CA into the proxy and validate the upstream certificate’s name.

Nginx Proxy Manager (NPM)

Create a Proxy Host with Forward Scheme https, the AlreadyOn service/address and port 19900. Configure the public certificate at NPM. For verified private-CA upstreams, mount the CA read-only and configure trusted CA, SNI and certificate-name verification in the effective nginx proxy configuration. Preserve the external Host header. An nginx example of the required upstream settings is:

proxy_set_header Host $http_host;
proxy_ssl_verify on;
proxy_ssl_trusted_certificate /etc/nginx/alreadyon-ca.pem;
proxy_ssl_server_name on;
proxy_ssl_name alreadyon.internal.example;

Replace the example name with one covered by the upstream certificate; it can differ from the Docker service hostname. NPM generates location blocks, so inspect its effective configuration: do not blindly paste a duplicate Host directive into a context that already sets it. A green public certificate indicator alone does not prove upstream validation. See NPM advanced configuration and nginx upstream TLS directives.

Traefik

For passthrough, use a TCP router with TLS passthrough and an SNI rule that sends to port 19900; AlreadyOn owns the viewer-facing certificate. For HTTP routing, use an HTTPS load-balancer server, preserve the external Host, and attach a ServersTransport that supplies the upstream certificate name and trusted CA. A file-provider transport/service fragment looks like:

http:
  serversTransports:
    alreadyon:
      serverName: alreadyon.internal.example
      rootCAs:
        - /etc/traefik/alreadyon-ca.pem
  services:
    alreadyon:
      loadBalancer:
        passHostHeader: true
        serversTransport: alreadyon
        servers:
          - url: https://alreadyon:19900

This is not a complete router/entrypoint/certificate-resolver configuration. Match the transport name/provider and mount the CA in your deployment; do not use insecureSkipVerify as a workaround. Consult Traefik ServersTransport and TCP TLS passthrough.

Identity and throttling behind a proxy

AlreadyOn ignores Forwarded, X-Forwarded-For/Host/Proto and X-Real-IP for client identity and does not support PROXY protocol. Authorization uses credentials; throttling uses the socket peer. HTTP-proxied viewers therefore share the proxy’s throttle bucket. TLS passthrough also normally exposes the proxy as the peer unless transparent routing preserves addresses. Keep direct LAN native sign-in available and restrict upstream access with your firewall.

08 / SWAGGER AND MANAGEMENT API

Swagger and management API

Open Server → API → Open Swagger UI, or the authenticated /api/docs/ route on your own server. The schema is available at /api/openapi.yaml. These are instance URLs, not pages on this website.

  1. Read the endpoint description, authentication and request/response schema.
  2. Start with a read-only GET on your own instance. Try it out sends a real request, not a simulation.
  3. For integrations, create a named API key in the API tab, copy it privately and revoke it when no longer needed. Keep it out of URLs and screenshots.
  4. Review write/delete operations carefully; do not experiment against live accounts/media to learn a schema.

Management API keys have owner authority. Playback tokens are separately scoped; never hand a management key to a player or external receiver. Swagger visibility does not bypass account/profile permissions. Use a temporary synthetic instance for destructive tests.

09 / BACKGROUND WORK, UPDATES AND BACKUPS

Background work, updates and backups

Dashboard shows Active Background Processes and playback sessions. Library polling finds changes, metadata jobs enrich catalog items, and scheduling extends future coverage while preserving published airings. Refresh Media requests an immediate scan; a large first scan can take time.

Optional Loudness Detection analyzes episode/movie/commercial audio using background workers, then applies normalization during playback. It does not rewrite originals or save normalized copies. Background work yields under sampled CPU, RAM, swap and disk pressure; these policies are not operating-system hard limits. Network-mounted media may need host traffic shaping if you require strict bandwidth limits.

Other maintenance includes automatic certificate renewal for managed modes, DDNS checks and inactive-session cleanup. Inspect their actual status and error timestamps rather than assuming a scheduled task succeeded. Missing metrics history after restart is unavailable data, not zero utilization.

Update the container

Read release notes, record the installed digest and back up persistent configuration/database with an application-consistent backup procedure. Coordinate downtime, then run:

docker compose pull
docker compose up -d
docker compose ps

Verify HTTPS, container health, mounts, sign-in, a representative channel and background status afterward. Keep the existing config volume. An old image digest is not a database downgrade plan; check schema compatibility before attempting rollback. App APK updates follow their own signed update flow.

Troubleshooting order

  1. Check host storage, permissions, container health and logs.
  2. Check local HTTPS, certificate names/trust and the media path.
  3. Test a known file and a second client; distinguish unsupported codecs from network or authorization failures.
  4. For remote problems, compare LAN access, DNS resolution and outside-network connectivity before changing the application.
  5. Share sanitized observations through Issues or ask a setup question there. Keep credentials, database exports and personal media private.
